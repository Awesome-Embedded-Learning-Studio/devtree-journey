# 我看我列张设备清单就挺好，怎么到你Linux还得长成一棵树?

## 一张设备清单为什么不够

你要是拿表格盘过设备的家底,这个念头我太懂了。咱们一行写一个设备,名字、地址、时钟都写在行里,你说直白不直白?咱们在“为什么需要设备树”那篇里就说了,硬件的描述要独立成数据,那最省事的想象可不就是一张清单?

行不行咱们不靠感觉,当场拿一个带连接的例子来试。板上焊了一颗温度传感器,挂在本板的 I²C 总线上,而 I²C 控制器做在 SoC 里。咱们按清单的写法给它们各写一行,三行很快就写完了。可你回头一看就犯难了:传感器挂在哪条 I²C 总线上,清单没地方放这句话,你得自己记着。设备树把这层关系直接放进结构里:传感器节点写在 I²C 控制器节点的里面,你顺着往上一层,就知道它挂的是哪条总线。

咱们用一小段教学片段看这个形状。设备和名字都是虚构的,你只看层次,语法咱们一概不究:

```dts
/* 教学片段:虚构设备,只看层次 */
/ {
    soc {
        serial@1000 { /* 串口控制器 */ };
        i2c-controller {
            temp-sensor { /* 挂在这条总线上的传感器 */ };
        };
    };
    chosen { /* 不是设备,下面细说 */ };
};
```

这棵树的规则咱们分三层说清。**根节点 `/` 是整棵树的入口**,其余的节点都从它展开。**节点**指的是一个设备、一个硬件功能,或者一份相关的描述。**属性**就是写在节点上的“名字 = 值”,咱们用它给节点存信息。**父子关系**经常对应的就是总线或组织关系,清单没地方放的那层连接,树直接画进了结构里。

## 树上不全是设备

你数一数上面的片段:四个节点里,你只数得出一个半“设备”。咱们把两类特殊的挑出来讲。

`soc` 这类节点其实是**容器**,把芯片里的控制器归拢在一起,而它自己不是设备。`chosen` 更是个好反例:规范明确说它不代表系统里的真实设备,只记录固件在启动时选择或指定的参数,比如咱们常见的内核命令行。所以“每个节点都是一颗芯片”的说法,咱们不能说满。多数节点描述的是设备或功能,剩下的少数是容器和信息节点。

还有一条边界:父子关系表达的连线,并不覆盖全部的硬件关系。时钟、电源这类跨节点的依赖,设备树用节点之间的**引用**来表达,说的就是“这个设备用谁的时钟”。引用的写法留给后面的章节,你现在只要知道“树上有父子以外的连接表达”这回事就够了。

## 四方怎么接上:硬件、设备树、binding、驱动

描述有了,约定谁定、活谁干?咱们把四位角色摆到一张桌上。

| 角色     | 交付什么   | 一句话定位           |
| -------- | ---------- | -------------------- |
| 实际硬件 | 真实能力   | 焊在板上的事实       |
| 设备树   | 事实的描述 | 一份独立数据         |
| binding  | 描述的约定 | 规定这类硬件该怎么写 |
| 驱动     | 操作的实现 | 内核里的代码         |

binding 是最容易被人误会的,咱们多说两句。它说的是“某类硬件应该怎样被描述”这样的约定,整套内容写成结构化的文档,还配了校验工具,属性不合规是会被查出来的。它不是另一份驱动的代码,也不是哪个驱动的私有配置。顺带分清一个英语撞名:设备树这边说的 binding 指描述约定,内核文档里另有一个同名的“driver binding”,指的才是设备和驱动建立关联那件事,跟咱们这边说的是两码事。

四方里最忙的接头是 `compatible`。规范对它的定义是:一个或多个字符串,刻画这个设备的具体**编程模型**。换成咱们的话说,它声明的就是“我跟哪种硬件操作方式兼容”。内核拿声明去匹配支持它的驱动,匹配上了,驱动才接着查它的资源、做初始化。咱们把三件事分开说:它不是节点的名字,真正的名字是 `serial@1000`,它也不是驱动源码的文件名,更不能靠乱填一个现成值把不兼容的硬件变成兼容的。兼容是硬件的事实,声明只是把它说了出来。

咱们看一个普通设备从描述到跑起来的概念顺序:内核读到描述,按平台和总线规则建立相应的设备,匹配支持它的驱动,驱动检查了资源并初始化。这是常见的路径,不过不是处处如此。内存、CPU、早期控制台各有各的路,匹配成功代表的也只是“认了亲”,初始化成不成功还要看资源是不是给对了。

## 描述换来了什么,换不来什么

咱们回到“为什么需要设备树”那篇里的板 A 和板 B,盘点独立描述换来的收益:在内核已有支持的前提下,换一块板常常只是换一份新的描述,而不必重编内核。SoC 级的公共信息可以做成共享片段,各板的描述只补差异。共享片段的名字叫 `.dtsi`,“DTS、DTB、dtc 都是什么”那篇的末尾再跟你正式介绍。硬件事实是集中放在一处的,咱们查起来、改起来都清爽。

“不行”的三句话,咱们也要讲明白,每句都回到四方的职责。硬件在、描述也是对的,内核就是没有这个驱动:描述变不出缺失的实现,数据填不了代码的缺口。驱动是有的,描述却把资源写错了:初始化可能失败,或者看着在跑、其实带病工作。节点写了 `status = "okay"`,设备压根没焊:数据改不了电路,纸面上的存在变不成物理存在。

所以准确的说法是:在内核已支持的前提下,不少硬件描述的调整不必重编内核,但描述改完了就要重新生成 DTB,并让启动流程用上新的产物。描述产物会经过启动阶段的软件再到 Linux,U-Boot 这样的引导器就可能读取、修改、传递它,细节咱们留到“谁会使用设备树”那篇的主场再讲,这里只留一条概念线:描述产物交给启动阶段的软件,再由它交到 Linux 的手里。咱们也不把 U-Boot 说成所有板子的必经之路。

描述的形状和生态咱们都过了一遍。接下来咱们要去的那篇是“DTS、DTB、dtc 都是什么”,咱们亲眼看描述的源码长什么样、亲手把它编译成产物。
