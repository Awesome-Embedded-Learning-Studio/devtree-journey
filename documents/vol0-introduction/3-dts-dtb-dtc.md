# 我看我写个文本把硬件交代清楚就行，怎么到你Linux还得编译一遍?

你要是写过 INI、YAML 这类配置文件,这个念头太正常了。你想着描述硬件嘛,听着就是写文档的活,怎么到你 Linux 这边,源码、编译器、二进制产物给你凑成了一套,跟 C 语言一个待遇?

答案是：因为你写下的文本,真正的读者是启动阶段的软件,人读起来顺不顺眼反倒是次要的,它要的是紧凑又好解析的格式。所以人写的源码得过一道编译才能用,这道工序里的三个名字,咱们挨个认个脸。

## 三个名字排开

- DTS(device tree source):人写的文本源码,描述那棵树。
- DTB(device tree blob):DTS 编译出来的二进制产物,给启动阶段的软件读。
- dtc(device tree compiler):干编译这件事的工具,上游实现在 kernel.org。

咱们把管线说成一句话:mini.dts 经 dtc 编译成 mini.dtb,启动阶段的软件读取 mini.dtb。反方向的路咱们也能走,让 dtc 把 DTB 反编译回 DTS 就行了。

本仓库的贯穿示例是一份十四行的 mini.dts。咱们把它从整体读到细节,最后你还要亲手把它编译一次。

## 看整体

咱们要读的源文件在仓库的 [mini.dts](../../edtc/example/00_bootstrap/mini.dts),你看到的全文就在下面:

```dts
/dts-v1/;

/ {
	compatible = "edts,a_demo";        /* 字符串属性 */
	#address-cells = <1>;            /* 单个 u32 cell */
	#size-cells = <1>;

	serial@1000 {                    /* 带单元地址的子节点 */
		compatible = "acme,uart";
		reg = <0x1000 0x100>;    /* 两个 cell */
		clock-frequency = <115200>;
		status = "okay";
	};
};
```

你一眼看不懂很正常,咱们只看形状就好:一层大括号套一层大括号,树就是这样搭起来的,`/` 是你的根。挂在根上的是 compatible、#address-cells 和 #size-cells 这几个属性,咱们挨个认过去。`serial@1000` 是根里面唯一的子节点,它自己又挂了四个属性,咱们能看到 compatible、reg,clock-frequency 和 status 都写在里面了。“设备树长什么样”那篇里咱们讲过,父子关系承载的是连接,属性记录的是信息,你在 mini.dts 里看到的,正是那套规则的第一次实战。

节点下面挂着的一行行“名字 = 值”,咱们叫它属性(property)。

## 逐行读懂

**第 1 行 `/dts-v1/;`** 是给编译器看的版本声明,咱们把它读成“本文件按 DTS 语法版本 1 来写”,跟硬件没什么关系。

**第 3 行 `/ {` 到末行 `};`** 圈出的是根节点。咱们把根节点看成机器本身,因为机器只有这么一个根,后面咱们要认的所有节点都挂在它下面。

**`compatible = "edts,a_demo";`** 声明的是机器的身份,正是咱们在“设备树长什么样”那篇细讲的 compatible。它的值是个字符串,咱们照惯例写成“厂商,设备”,拿逗号切开看:前面是谁家的,后面是什么。真实世界的厂商前缀有一份公开维护的名单,咱们这里的 edts 是虚构的示例。

**`#address-cells = <1>;` 与 `#size-cells = <1>;`** 全文件最不像人话的就是这两行,可 reg 怎么读,偏偏是它们说了算。咱们把 cell 认下来:它是设备树里数字的基本计量单位,一个 cell 就是一个 32 位的大端整数,大端的意思是高位字节排在前面。这两行定下的规则,管的是本节点下面所有子节点,咱们读子节点的时候,地址用 1 个 cell 写,长度用的也是 1 个 cell。

**`serial@1000 {`** 是根节点下唯一的子节点。@ 前面的 serial 是节点的名字,你读作“串口”就对了。@ 后面的 1000 叫单元地址(unit address),它声明的是这个设备住在父节点地址空间的 0x1000 处。

**`reg = <0x1000 0x100>;`** 尖括号里包着的是两个数,说的是寄存器区域从 0x1000 开始,长度的值是 0x100。为什么恰好两个数,每个又按 32 位理解?咱们回头看上面两行就明白了,因为地址占的是 1 个 cell,长度占的也是 1 个 cell,而一个 cell 就是 32 位。咱们要是换一块把 #address-cells 和 #size-cells 都声明成 2 的板子,同样的 reg 就得写四个数。规则一变咱们的读法就得跟着变。

**`clock-frequency = <115200>;`** 存的是串口的时钟频率。115200 你大概眼熟,它是常见的波特率数字,波特率指的是串口每秒传输的位数。咱们在源码里把它写成十进制,它进了 DTB 就是一个 32 位的大端整数。

**`status = "okay";`** 是设备树里的标准属性,okay 表示的是设备启用。咱们想让内核当它不存在,把它改成 disabled 就行了。

十四行到这里咱们就读完了。你合上文章,对着原文件用自己的话把每条解释说一遍,每一条你都说得出来,这一篇就算读到位了。

## 动手:亲手编译一次

动手环节要用你电脑上的 dtc 和 xxd(用十六进制查看文件字节的工具),本仓验证的版本是 dtc v1.8.1(2026-10-11)。你在仓库的 [exercises/lab/00-bootstrap](../../exercises/lab/00-bootstrap/README.md) 目录执行,输入文件的唯一来源在 edtc 工程里(本仓自研的工具工程,文末咱们再细说),实验就不另立副本了:

```shell
dtc -I dts -O dtb -o mini.dtb ../../../edtc/example/00_bootstrap/mini.dts
ls -l mini.dtb
xxd mini.dtb | head -3
```

下面是咱们在本机真跑的输出(dtc v1.8.1,咱们验证的日子是 2026-10-11)。`ls -l` 的显示格式随系统不同,你要认的数字只有一个,就是它的大小:293 字节。

```output
00000000: d00d feed 0000 0125 0000 0038 0000 00e4  .......%...8....
00000010: 0000 0028 0000 0011 0000 0010 0000 0000  ...(............
00000020: 0000 0041 0000 00ac 0000 0000 0000 0000  ...A............
```

有两处值得咱们停下细看。开头四个字节 `d00d feed` 是 DTB 的魔数,机器认格式靠的就是它,“DTB 排成哪几块,目录住在哪里”那篇讲文件头时咱们还会见到它。中段和尾段里咱们肉眼就能认出源码里的字符串:

```output
00000070: 0000 001a 0000 0001 0000 0001 7365 7269  ............seri
00000080: 616c 4031 3030 3000 0000 0003 0000 000a  al@1000.........
00000090: 0000 0000 6163 6d65 2c75 6172 7400 0000  ....acme,uart...
```

```output
000000d0: 6f6b 6179 0000 0000 0000 0002 0000 0002  okay............
000000e0: 0000 0009 636f 6d70 6174 6962 6c65 0023  ....compatible.#
000000f0: 6164 6472 6573 732d 6365 6c6c 7300 2373  address-cells.#s
```

中段里咱们能看到节点的名字 `serial@1000`,还有熟悉的属性值 `acme,uart`,都是咱们源码里写过的。尾段里你还能认出属性值 okay,以及咱们用过的属性名,compatible、#address-cells 这些你都眼熟。你写下的源码文本以字节的形式住进了产物各处,但整个文件已经成了二进制,不再是咱们写的文本。这些字符串分别住在哪个区块、为什么这样安排,“末尾两块的地盘怎么圈”那篇给咱们揭晓。

反方向咱们也能走:

```shell
dtc -I dtb -O dts mini.dtb
```

咱们拿到的输出:

```dts
/dts-v1/;

/ {
	compatible = "edts,a_demo";
	#address-cells = <0x01>;
	#size-cells = <0x01>;

	serial@1000 {
		compatible = "acme,uart";
		reg = <0x1000 0x100>;
		clock-frequency = <0x1c200>;
		status = "okay";
	};
};
```

咱们对照着看,结构全都回来了,注释则留在了源码里。还有一个细节值得你留意,源码里的十进制 115200 回来变成了十六进制 0x1c200,`<1>` 变成了 `<0x01>`。值是没变的,写法变了。所以这里要把边界立好:反编译还原的是结构与值,还原不了注释和源码写法。你拿它检查“树长什么样、值是多少”是可靠的,把它当源码还原就不对了。

## 顺带认一个 .dtsi

知道头文件对吧。其实是一路人哈哈哈。

.dtsi 文件装的是公共片段,咱们在 .dts 里可以引入它。典型的用法是这样:芯片厂商提供的是一份 SoC(片上系统,也就是把 CPU 与外设打包在了一颗芯片里)级别的 .dtsi 描述,板卡厂商的 .dts 把它引进来,再补上这块板子自己的设备。细节咱们都收在“一堆文件怎么分工才算管得住”的那篇里,这里咱们跟它混个脸熟。

咱们的术语依据如下:cell 的 32 位大端定义、单元地址与厂商前缀惯例,出自 Devicetree Specification v0.4 的本仓缓存副本。命令输出是咱们本机真实运行的,验证用的环境是 dtc v1.8.1。
