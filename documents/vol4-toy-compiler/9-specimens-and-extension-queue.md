# 真树标本读出什么差距,扩展的队伍怎么排?

咱们这一卷的前两章把玩具的家底盘完了。“怎样读懂一小部分 DTS”那章定下了第一版文法,一个根节点带嵌套的子节点,属性的值写法认了几种,超界的语法一律打回。“标签和引用怎样变成二进制”那章补上了连线,标签是源码层的名字,phandle 是产物里的编号,悬空的引用咱们要拦,重复的标签也不放行。两章下来的玩具一直靠几十行的小夹具过日子,咱们喂进去什么,它编出来的就是什么,边界全在咱们自己手里。

可是真实的板卡树不吃这一套小灶。内核里的一份板级描述动辄几百行,include 套了好几层,宏写满了属性值,顶格的 & 块一写就是十几处。咱们这一章来收第四卷的尾:真标本咱们找了两份,读它的组织,量玩具与真实的差距,支持矩阵立了起来,定下拒绝的路数,扩展路线也照正本排成了队。动手的位置照旧在 /tmp,你在自己电脑上建一个工作目录:

```shell
mkdir -p /tmp/vol4ch15/dts
cd /tmp/vol4ch15
```

本仓验证的工具是 dtc v1.8.1,预处理用的 cpp 来自 GCC 16.2.1,咱们跑命令的日子是 2026-10-18。

## 真标本到手:2011 年的板卡树读起来什么感觉

咱们挑的板子叫 i.MX51 Babbage,Freescale 自家的参考板,2011 年就进了内核主线。硬件的背景一句话就够:Cortex-A8 的 SoC 拖着一板外设。咱们挑它,图的正是年头的跨度:2011 年的写法看得到,2026 年的演进也不缺,同一块板在咱们手里当两面镜子。两版摘录缓存在本仓的 .claude/materials/kernel-excerpts/ 里,目录是 git 不跟踪的本地材料,正文里咱们照内核源码树的路径称呼它们:

- v3.7:`arch/arm/boot/dts/imx51-babbage.dts`,配同目录的 `imx51.dtsi` 与 `skeleton.dtsi`
- v7.2.9:`arch/arm/boot/dts/nxp/imx/imx51-babbage.dts`,配同目录的 `imx51.dtsi`

咱们从老的那版读起。板级的入口文件总共 267 行,头几行就把它的组织方式交代了:

```dts
/dts-v1/;
/include/ "imx51.dtsi"

/ {
	model = "Freescale i.MX51 Babbage Board";
	compatible = "fsl,imx51-babbage", "fsl,imx51";
```

引文件的指令 `/include/` 就跟在 `/dts-v1/` 后头,它是 dtc 自己的编译器指令,“怎样描述和组织设备”那章里咱们靠它把公共描述拼过树。被引的 imx51.dtsi 有 434 行,它的头上一行又是一条 `/include/ “skeleton.dtsi”` 指令,13 行的它把根节点和默认的 cells 声明铺好。摞起来的三个文件一共 714 行,这就是一棵 2011 年板卡树的全部家当。你拿教学例子一比,分量就掂出来了:第一卷的 soc.dtsi 才 20 行出头,密度的差距是数量级的。

咱们量的还不止行数。咱们拿 grep 数过几遍:dts 加 dtsi 的标签写了 42 个,引用写了 28 处,空属性数出了 34 处,两个文件里同名的节点有 15 个。教学夹具里的标签一只手数得完,标本里的标签一抓就是一大把。

同名节点是咱们要停下来的地方。imx51.dtsi 里的 uart1 是芯片级的描述:

```dts
		uart1: serial@73fbc000 {
			compatible = "fsl,imx51-uart", "fsl,imx21-uart";
			reg = <0x73fbc000 0x4000>;
			interrupts = <31>;
			status = "disabled";
		};
```

板级文件里咱们又写了一个 uart1,与 dtsi 里的名字和路径都对得上:

```dts
		uart1: serial@73fbc000 {
			pinctrl-names = "default";
			pinctrl-0 = <&pinctrl_uart1_1>;
			fsl,uart-has-rtscts;
			status = "okay";
		};
```

两段在源码里各过各的日子,编译的时候怎么合,咱们到讲节点合并的那篇对着产物看。你眼下只要认下一件事:板级文件不复制芯片级的描述,它只往同名的节点里补板子自己的东西。

## 隔十五年再看同一块板,树换了什么活法

咱们再看 v7.2.9:它的 imx51-babbage.dts 搬过了家,住进了 nxp/imx/ 子目录,行数涨到了 718,比 v3.7 的板级文件厚了将近一倍。头几行就换了一副活法:

```dts
/dts-v1/;
#include "imx51.dtsi"

/ {
	model = "Freescale i.MX51 Babbage Board";
	compatible = "fsl,imx51-babbage", "fsl,imx51";

	chosen {
		stdout-path = &uart1;
	};
```

引文件的指令换成了 `#include`,认它的是 C 预处理器 cpp,dtc 已经不认它们了。咱们看树里的数字,写法也换了个样:GPIO 的极性写成 GPIO_ACTIVE_HIGH 一类的名字,引脚复用整段换成 MX51_PAD_ 打头的宏,光后一种就用了 131 处。键盘矩阵更进了一步,MATRIX_KEY 是带参数的宏:

```dts
		linux,keymap = <
			MATRIX_KEY(0, 0, KEY_UP)
			MATRIX_KEY(0, 1, KEY_DOWN)
			MATRIX_KEY(0, 2, KEY_VOLUMEDOWN)
			MATRIX_KEY(0, 3, KEY_HOME)
		>;
```

节点的名字也换成了通用写法。咱们手里的标本里,板上的 DataFlash 写成了 flash@1,不再拿 at45db321d 的型号当名字。芯片级 dtsi 里的两个节点也照着改了,引脚控制器写成了 pinctrl@73fa8000,NAND 控制器写成了 nand-controller@83fdb000,型号都退到了 compatible 里。引脚的分组直接挂在 &iomuxc 的标签名下,中间不垫板名的包装节点。

变化最大的是改配置的路数,咱们细看。v3.7 的路数是把根节点再写一遍往里塞板级内容,v7.2.9 的板级文件末尾挂着 19 个顶格的 & 块,谁要改就顶到谁的名下:

```dts
&uart1 {
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_uart1>;
	uart-has-rtscts;
	status = "okay";
};
```

咱们把两版的差别摆成一张对照表,后面量差距的时候直接引用:

| 写法 | v3.7,2011 年 | v7.2.9,2026 年 |
| ---- | ------------ | ------------- |
| 引文件 | /include/,dtc 自己搬 | #include,交给 cpp |
| 宏 | 不用,数字手写 | dt-bindings 头文件,还有带参宏 |
| 节点名 | 型号入名,如 at45db321d@1 | 通用名为主,如 flash@1 |
| 板级改配置 | 重写同名节点 | 顶格 & 块,19 处 |
| 标签与引用 | 70 处(42 标签,28 引用) | 308 处(118 标签,190 引用) |
| dts 行数 | 267 行 | 718 行 |

两版之间隔着十五年的工程习惯,咱们读起来还是同一副骨架,节点、属性、标签、引用的老底子都没动,组织的方式越来越倚重 cpp 与合并。咱们量出来的差距正好落在 cpp 与合并这两样上。

标本咱们读完了,差距也数了出来,咱们量出的行数、标签与引用都指向同一件事:真实树的主干在组织,而组织的手段全落在咱们子集的外面。下面咱们回到自己的玩具上,看这些手段怎么排进扩展的队伍。

## 能力怎么扩:include、节点合并与删除排成队

正本规格给 edtc 排的扩展方向有四样,含 include 的搬运、节点的合并、删除指令、预处理接入,每一样都有 dtc 的现成语义可以照着量。代码的情况咱们照实说:edtc 的实现在仓库里还停在 M0 附近,这一段连同后面的设计讨论都是图纸,能跑的代码还在图纸之外。

咱们把 include 排在最前头,因为它的活最薄。`/include/` 干的活就是把被引文件的原文本搬进来,一层套一层的语义等价于文本的拼接,dtc 给它配了 -i 的查找路径。咱们 DTS 前端的实现位置同样在词法层:lexer 拿到 `/include/` 就切换自己的输入源,token 流还是连续的,报错的位置跟着文件切换走。v3.7 的三层 include 链,它就是将来排期的验收夹具。

节点合并的分量厚一些,它动的是树模型。咱们把 v3.7 的两段 uart1 合起来编译再反编译,产物里的节点长这样:

```dts
			serial@73fbc000 {
				compatible = "fsl,imx51-uart", "fsl,imx21-uart";
				reg = <0x73fbc000 0x4000>;
				interrupts = <0x1f>;
				status = "okay";
				pinctrl-names = "default";
				pinctrl-0 = <0x09>;
				fsl,uart-has-rtscts;
			};
```

咱们对着产物把合并的规则数清:dtsi 里的 compatible、reg、interrupts 原样都在,板级新加的 pinctrl-names、pinctrl-0、fsl,uart-has-rtscts 也进来了,status 被板级的 okay 盖掉了旧的 disabled,同名属性后写的赢。还有一处咱们容易看漏:两处定义写的是同一个标签 uart1,合成的节点还是原来那个、标签也不冲突,往同一个节点上重复挂标签是合法的写法。标签要是挂到了两个不同的节点上,咱们在讲拒绝测试的那篇里就会看到 dtc 的报错。

删除指令的分量最薄,牵出的决定却最深。`/delete-node/` 和 `/delete-property/` 的语义就是从树上摘节点、摘属性,“怎样描述和组织设备”那章里咱们用过它们裁掉不合身的公共描述。两版的标本都没用上它们,可它们在真实的项目里到处都在,咱们的排期不能省。排的时候必须连边界一起定:删一个不存在的节点,dtc 一声不吭地通过,咱们的玩具要不要这么宽容,咱们把它记进拒绝原则一起裁决。

## 预处理接入:分工在咱们手里接上最后一棒

“构建系统实际上做了什么”那章里咱们把内核构建的接力看全了:cpp 干的是文本的活:搬文件、展开宏、留下行标记,dtc 只吃处理完的纯 DTS。到了自己的玩具上,同一套分工在咱们手里原样搬过来:edtc 不认井号的指令,预处理交还给了调用方,咱们的输入约定就是 cpp 的输出。第一卷留下的分工,到这里在咱们自己的工具上接完了最后一棒。

输入的约定里最要紧的是行标记。cpp 会把 `# 1 “nxp/imx/imx51.dtsi” 1` 这样的笔记写进中间文件,dtc 是认得它们的,报错才能顺着笔记指回原始文件的原始行。“构建系统实际上做了什么”那章里咱们验过一回,宏没展开的时候,dtc 的报错顺着行标记落回了 dtsi 的原行。咱们的 DTS 前端照同样的约定解析行标记,把它存进节点的位置信息,再与 dtc 的报错位置对拍,这就是预处理接入的验收材料。

预处理接入的成本还有一层,咱们在 v7.2.9 的实验里亲眼看到了:cpp 展开带参的宏之后,交出来的纯 DTS 里会混进表达式。MATRIX_KEY 展开后的样子是带位运算的长式子,而第一版子集的文法里没有表达式。所以接住 cpp 的输出,就得把表达式的文法排进路线,或者对接上来的表达式明确拒绝。躲是躲不掉的,真实的板卡就长这个样子。

四样的图纸到这里画完了:include 的活最薄,合并动的是树模型,删除牵出的决定最深,预处理带出了表达式的难题。图纸要变成对外说得清的承诺,还得有一张一行一行写清状态的表,下一篇咱们就立支持矩阵,再看接不住的输入怎么拒绝。
