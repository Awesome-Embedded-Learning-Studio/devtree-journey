# 内存保留区的条目长什么样,末尾两块的地盘怎么圈?

上一篇收尾的时候,三道加减法咬合过了,文件头成了你能信的目录。目录里圈出的三块地盘,咱们这一篇按文件里的次序进头一块,把它的活儿和条目格式讲清楚,再编一个真带 /memreserve/ 的源文件,亲眼看一条真实的保留条目怎样住进产物,末了把结构块和字符串块的地盘也圈出来。

## 内存保留区:16 字节一条,全零收尾

文件头之后住的块就是内存保留区,它的活儿规范在 5.3 节讲得直白:向接下来消费产物的程序报备一批物理内存区间,这些区间有别的主人,消费的一方不许把它们当一般的内存来分配。规范举的例子是 IOMMU 的地址翻译表,还有固件在运行期要接着用的代码和数据。咱们上一篇读到的 0x28,说的就是它的起点。

咱们再看条目的格式,规范定得很死:每条的身材都是 16 字节,前 8 字节是区间的物理地址,后 8 字节是区间的长度,两个数用的都是 64 位大端。整个条目表的收尾也定死了:地址和长度全为 0 的条目就是终点,读表的人见到了它就停。还有一条对齐的要求:保留区从文件头算起要落在 8 字节对齐的偏移上,40 恰好是 8 的倍数,所以它紧贴着文件头住下了。

有一个细节值得咱们单独指出来:文件头没给保留区记大小的字段,结构块和字符串块各有自己的 size,保留区却没有 size_dt_rsvmap 这样的字段。它的实际长度不写在头里,你得分条数到全零收尾才知道。咱们手工算 40 加 16 的时候,用的正是这个读法。

条目的长相咱们看过了,接下来咱们造一个真带保留区的源文件,亲眼看它编进产物的样子。/memreserve/ 写在源文件的顶层,和根节点是平级的,一行记的就是一条。咱们保留 0x10000000 起的 1 MiB:

```dts
/dts-v1/;

/memreserve/ 0x10000000 0x00100000;

/ {
	compatible = "edts,a_demo";
};
```

咱们把上面的源码存成 rsv.dts,编出来再看它的字节:

```shell
dtc -I dts -O dtb -o rsv.dtb rsv.dts
wc -c rsv.dtb
xxd -g4 -l 72 rsv.dtb
```

```output
123 rsv.dtb
00000000: d00dfeed 0000007b 00000048 00000070  .......{...H...p
00000010: 00000028 00000011 00000010 00000000  ...(............
00000020: 0000000b 00000028 00000000 10000000  .......(........
00000030: 00000000 00100000 00000000 00000000  ................
00000040: 00000000 00000000                    ........
```

0x28 往后的 32 个字节,咱们逐对读:

- 0x28 起的 8 字节是 00000000 10000000,大端读出地址 0x10000000。
- 0x30 起的 8 字节是 00000000 00100000,读出长度 0x100000,换算十进制是 1048576,正好 1 MiB。
- 0x38 起的 16 字节全是零,这就是收尾条目,表到此为止。

源文件里写的两个数,字节里都验上了。你再抬头看文件头:off_mem_rsvmap 还是原来的 0x28,保留区依旧紧跟在文件头的后面,它的起点没理由挪。off_dt_struct 却从 0x38 变成了 0x48,真实条目把自己 16 字节的身高记进了布局,住在后面的结构块就被顶后了 16 字节。新产物的文件头,咱们照样拿加减法咬一遍:

```shell
echo $((0x48 + 0x28)) $((0x70 + 0x0b))
```

```output
112 123
```

72 加 40 得到的 112 是 off_dt_strings 的值,咱们再往前数,字符串块用 11 字节正好把 123 字节的文件用完。这套验收的办法,咱们换一份产物还能接着用。

保留区的读法到此就齐了:条目的身材、收尾的记号,还有数条目量大小的路数。文件里排在后面的还有结构块和字符串块,它们的地盘咱们接下来就圈。

## 结构块和字符串块:这里只圈地盘

排在末尾的结构块和字符串块,地盘咱们从文件头里已经圈出来了:结构块占了 56 到 228 之间的 172 字节,字符串块占了 228 到 293 之间的 65 字节。它们的内部结构,咱们按卷的分工留给“如何安全遍历所有节点”那章:结构块里住的是五种记号,树的嵌套摊平在记号的接龙里,字符串块存的是全部属性的名字,取名字的办法是拿偏移到这里查。这一篇你要带走的是定位的本事,定位靠的就是文件头里的四个数,两个偏移和两个大小的字段。

光靠数字圈出的地盘,咱们再贴一层证据。你拿 -s 选项让 xxd 从 0xe4 起步 dump,字符串块的第一眼你就认得:

```shell
xxd -s 0xe4 mini.dtb
```

```output
000000e4: 636f 6d70 6174 6962 6c65 0023 6164 6472  compatible.#addr
000000f4: 6573 732d 6365 6c6c 7300 2373 697a 652d  ess-cells.#size-
00000104: 6365 6c6c7300 7265 6700 636c 6f63 6b2d  cells.reg.clock-
00000114: 6672 6571 7565 6e63 7900 7374 6174 7573  frequency.status
00000124: 00                                       .
```

228 号字节起步的地方摆着的是 compatible 的 ASCII,跟着的 #address-cells、#size-cells、reg、clock-frequency、status,全是你源码里写过的属性。每个名字后面那个 00 是字符串的结尾,规范管它们叫以空字符结尾的字符串,咱们读它的时候数到 00 为止。数到 0x124 的最后一个 00,65 字节正好用完了,文件也正好到了头。每个名字在产物里都只存了一份,谁在引用这些名字、怎样引用的,你到下一章都会看到。

结构块里的那 172 个字节,咱们整章一个都还没读,树到底怎样摊平在 0000 0001 这样的记号里,悬念就留到了下一章。咱们整章读下来,你拿到手的是一份地图:四大块的次序、文件头的十个字段,还有不靠解析工具的验收办法。往后整卷的活:读字节、建树模型、再写回 DTB,都是在地图上开工,咱们下一章就从 0x38 的第一个记号进去。

<summary>参考答案(想好再展开)</summary>

1. 一条 16 字节,前 8 字节是地址,后 8 字节是长度。靠地址和长度全为 0 的条目收尾。mini.dtb 的保留区只有收尾条目,占 16 字节。
2. off_dt_struct 从 0x38 变到了 0x48,totalsize 也记下了新的排布。off_mem_rsvmap 没变,因为保留区依旧紧跟在 40 字节的文件头后面。
3. 两个偏移加两个大小:off_dt_struct、size_dt_struct、off_dt_strings、size_dt_strings。结构块占 56 到 228 之间的 172 字节,字符串块占 228 到 293 之间的 65 字节。
4. 存的是全部属性的名字,每个名字以空字符 00 结尾。能读到 compatible、#address-cells、#size-cells、reg、clock-frequency、status。
