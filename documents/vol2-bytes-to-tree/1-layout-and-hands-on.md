# 一份 DTB 从头到尾排成什么样,前 40 个字节怎么亲手读出来?

“改一行 DTS,产物发生了什么”那章收尾的时候,咱们把一件事托付给了讲格式的卷:你改的那个值为什么恰好住在 0xc0,产物里的区块又是怎么划分的。“构建系统实际上做了什么”那章给第一卷收了官,编译、反编译、xxd 看字节三样手艺你都练熟了,咱们现在就来兑现。第二卷的名字是“从字节到自己的树”,它要把咱们从产物的外面带到里面,把每个字节住的地方认清楚,末了还要亲手写一个读 DTB 的 reader。

咱们从最上层的骨架讲起。按规范 v0.4 第 5 章的说法,DTB 是一份线性的、无指针的二进制,产物的全貌分成四大块,咱们拿一张图把它认全,再把文件头的十个字段逐个过掉。实验部分你只靠 xxd 和 shell 的算术,亲手把 293 字节产物的前 40 字节解出来,验到每一个数都对上了才算过关。

## 四大块从头排到尾,一张图认全

规范给这套二进制起的名字是扁平化的设备树(Flattened Devicetree),咱们要抓的关键词是线性、无指针:整份数据从头到尾排成了一条直线,块与块的连接不靠指针,靠的是偏移。四个块的分工是这样的:

- 文件头(header)固定 40 字节,十个字段是整份文件的目录,块的位置和大小都在这里查。
- 内存保留区向消费方报备物理内存:哪些区间有主人,不许拿去当一般内存用。
- 结构块是树的本体,节点和属性摊平成一串记号(token),全住在这里。
- 字符串块是属性名字的仓库,结构块按偏移到这里取名字。

咱们把 mini.dtb 的实测布局画成一张图,图里的每个数,这一章结束前你都会亲手读出来:

```text
0x000 +----------------------------------------+
      | 文件头(header)        固定 40 字节    |
0x028 +----------------------------------------+
      | 内存保留区       16 字节,全零条目收尾 |
0x038 +----------------------------------------+
      | 结构块                  172 字节      |
0x0e4 +----------------------------------------+
      | 字符串块                 65 字节      |
0x125 +----------------------------------------+
```

图里有两处规范层面的细节,咱们交代在前面。规范允许块与块之间夹着空闲的字节,dtc 编出的产物却没有留,块与块都是首尾相接的,这个事实咱们稍后在字节上验出来。块在文件里的出现次序是内存保留区、结构块、字符串块,规范用的词是“应当”,dtc 照做了。

读这样一份文件的姿势也就定下来了:消费方拿到了产物,从偏移 0 读 40 字节的目录,再按目录里的偏移和大小,把三个块的地盘圈出来。咱们这一章干的活,跟消费方拿到文件的第一步是同一件事。

## 文件头:十个字段,整份文件的目录

文件头的定义在规范 5.2 节,给的是一段 C 结构体:十个字段,每个都是 32 位的整数,存储一律用大端的字节序。大端的读法你在第一卷就练过了,高位的字节排在前头,四个字节 `0001 c200` 拼出 115200 用的就是它,`d00d feed` 一眼好认也是沾了它的光。

十个字段咱们逐个过一遍,白话说的都是它管什么:

| 偏移   | 字段               | 它管什么                                   |
| ------ | ------------------ | ------------------------------------------ |
| `0x00` | `magic`            | 魔数,值恒为 `d00d feed`,读文件的开场暗号 |
| `0x04` | `totalsize`        | 整份文件的字节数,连文件头带全部块一起算   |
| `0x08` | `off_dt_struct`    | 结构块起点离文件开头的字节数               |
| `0x0c` | `off_dt_strings`   | 字符串块起点的偏移                         |
| `0x10` | `off_mem_rsvmap`   | 内存保留区起点的偏移                       |
| `0x14` | `version`          | 格式的版本号                               |
| `0x18` | `last_comp_version`| 向后兼容到的最早版本                       |
| `0x1c` | `boot_cpuid_phys`  | 启动 CPU 的物理 ID                         |
| `0x20` | `size_dt_strings`  | 字符串块的字节长度                         |
| `0x24` | `size_dt_struct`   | 结构块的字节长度                           |

表里有一处容易拧巴的地方,咱们点出来:字段在文件头里的排列次序,跟的是规范结构体的声明次序,`off_dt_struct` 排在 `off_mem_rsvmap` 的前面,而块在文件里的实际次序却是保留区在前。初读的时候你别把这两套次序混在一起,咱们把文件头当目录用,目录里字段的行序和块在文件里的摆放次序本来就是两回事。

版本的两个字段咱们多说两句。`version` 记的是格式自身的版本,规范 v0.4 描述的只有版本 17,dtc 1.8.1 编出的产物写的也正是 17,咱们这一卷拿它当主线,历史版本的差异就不展开了。`last_comp_version` 记的是向后兼容到的最早版本,版本 17 跟版本 16 是向后兼容的,所以这个字段按规范的要求恒写 16。

`boot_cpuid_phys` 咱们单独交代一句:它记启动 CPU 的物理 ID,规范要求这个值与那颗 CPU 节点 `reg` 属性里的值一致。咱们的演示树里没有 CPU 节点,dtc 就写了 0,指定它的办法也有,dtc 的 `-b` 选项就是干这个的。

十个字段的白话咱们过完了,字段的值你却一个都还没见过。接下来咱们就把实验兑现,你进 /tmp 拿 xxd 解产物的前 40 个字节,再用 shell 的算术验骨架的咬合。

## 动手:前 40 字节,咱们一组一组读

动手的环节咱们照旧搬进 /tmp 里做,目录名咱们就叫它 /tmp/vol2ch4,免得中间的产物混进仓库。命令咱们在本机真实跑过,输出也是原样贴在下面的,你照着走就能复现:

```shell
mkdir -p /tmp/vol2ch4
cd /tmp/vol2ch4
dtc -I dts -O dtb -o mini.dtb /home/charliechen/devtree-journey/edtc/example/00_bootstrap/mini.dts
wc -c mini.dtb
xxd -g4 -l 40 mini.dtb
```

```output
293 mini.dtb
00000000: d00dfeed 00000125 00000038 000000e4  .......%...8....
00000010: 00000028 00000011 00000010 00000000  ...(............
00000020: 00000041 000000ac                    ...A....
```

这回咱们给 xxd 添了两个新选项,各自的活儿是这样的:

- `-g4` 按 4 个字节一组报数,一组正好对上文件头的一个字段。
- `-l 40` 只报前 40 个字节,十个字段不多不少。

对上了号,咱们一组一组把字段读下去:

- 0x00:d00dfeed,magic,开场暗号对上了。
- 0x04:00000125,totalsize,十六进制的 125,十进制 293。
- 0x08:00000038,off_dt_struct,结构块从 56 号字节起步。
- 0x0c:000000e4,off_dt_strings,字符串块起点 228。
- 0x10:00000028,off_mem_rsvmap,保留区起点 40。
- 0x14:00000011,version,格式版本 17。
- 0x18:00000010,last_comp_version,兼容到版本 16。
- 0x1c:00000000,boot_cpuid_phys,演示树没有 CPU 节点,写 0。
- 0x20:00000041,size_dt_strings,字符串块 65 字节。
- 0x24:000000ac,size_dt_struct,结构块 172 字节。

十六进制换算和骨架的咬合,咱们交给 shell 的算术:

```shell
echo $((0x125)) $((0x38)) $((0xe4)) $((0x41)) $((0xac))
echo $((0x28 + 16)) $((0x38 + 0xac)) $((0xe4 + 0x41))
```

```output
293 56 228 65 172
56 228 293
```

第二行报的就是三道咬合。保留区的起点是 40 号字节,咱们的源文件没写 /memreserve/,区里只住了那个全零的收尾条目,40 加 16 得到的 56,正好就是 off_dt_struct 的值。结构块 56 加 172 得到的 228,正好就是 off_dt_strings 的值。字符串块 228 加 65 得到的 293,正好就是 totalsize 的值,咱们数到这里,文件也正好用完了。

三道加减法都咬合了,一个悬空的数都没有,文件头自己就把自己验完了。你还多了个不靠解析工具的验收办法:往后你拿到任何一份 DTB,你拿 xxd 解前 40 字节,该对上的数对不上,产物就出了问题。咱们未来的 DTB reader 开工的时候,头一批要做的也正是这些检查:magic 对不上就拒收,偏移加长度得出的终点也不许越过 totalsize。edtc 那边眼下的进度是 FileReader 和字节序的底座,reader 的本体还没动工,咱们现在做的,恰好是替它把验收的清单写清楚。

三道加减法咬合过的文件头,到此就成了你能信的目录。咱们按次序往下走,文件头后面紧贴着的就是内存保留区,下一篇咱们进去读它的条目,再编一个带 /memreserve/ 的源文件,看的是真实条目怎样改动布局。
