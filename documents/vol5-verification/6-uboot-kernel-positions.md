# 板子上和内核里怎么叠,三个位置又怎么挑?

上一篇把电脑上的实验收了尾。叠树的位置咱们还剩两处:板子的引导阶段能缝,内核跑起来之后咱们照样有办法缝,这一篇按文档的口径走。

## 板子上、内核前:U-Boot 的 fdt apply(未实测)

到了板子上,叠树的位置头一处是引导阶段。咱们本机没有板子,U-Boot 这边咱们没有实测,下面的口径出自 U-Boot 的官方文档,链接咱们放在了延伸阅读里,等你手头有了板子,你照着核一遍再信。

U-Boot 的壳里有 `fdt` 命令组,咱们用得最多的是 `fdt apply`,它专门管叠 overlay 的活。文档给的手工流程长这样,`=>` 是 U-Boot 的提示符:

```shell
=> env set fdtaddr 0x87f00000
=> env set fdtovaddr 0x87fc0000
=> load ${devtype} ${bootpart} ${fdtaddr} ${bootdir}/base.dtb
=> load ${devtype} ${bootpart} ${fdtovaddr} ${bootdir}/overlay.dtbo
=> fdt addr $fdtaddr
=> fdt resize 2000
=> fdt apply $fdtovaddr
=> bootm ${kerneladdr} - ${fdtaddr}
```

咱们把每一步的活儿读出来。load 把基础和 overlay 两份产物从存储读进了内存,`fdt addr` 把基础的住址报给 U-Boot,`fdt resize` 给基础树腾出长大的空位,它的参数按十六进制来读,因为叠进来的节点要让树变大,原地不动是塞不下的。`fdt apply` 干的活跟 fdtoverlay 同源:拿 overlay 的 fixup 去查基础的符号表,查到了就回填,缝合也就完成了。末了 bootm 带着缝好的树把内核请起来。

文档还有两条要紧的叮嘱。基础和 overlay 的编译都得带 `-@`,这一点跟咱们实验里的做法一致,文档还提醒 `-@` 需要 dtc 1.4.4 往上的版本。另一条是失败的处理:`fdt apply` 出错的时候,基础和 overlay 两份就都作废了,文档的建议是手边留副本,别拿仅有的原件去叠。

这边的适用场景:一份内核镜像伺候一个家族的板子。基础管的是核心板的描述,每块板子按自己的配件在启动脚本里叠对应的 overlay,产线上烧写不同的 overlay 文件,内核镜像保持一个版本就够用了。要全自动的话,文档指了 FIT 镜像的路子,overlay 也跟着镜像的配置自动应用,细节咱们不铺开。

## 内核里:overlay API(未实测)

第三个位置落在了内核运行起来之后。内核文档 overlay-notes 讲的是内核里的 C API,咱们同样未实测,出处链接咱们放在了延伸阅读,下面按文档的口径转述。

入口的函数是 `of_overlay_fdt_apply()`:咱们调用它的时候,把展开好的 overlay 产物和它的大小递进去,它把 overlay 应用到内核正在使用的那棵活树上,返回一个 cookie 作为这次应用的凭证。撤销的路子走 `of_overlay_remove()`:咱们拿 cookie 找回来,内核把这段增量从活树上摘了下去,该注销的设备跟着注销。文档还备了 `of_overlay_remove_all()`,咱们用它一次撤干净。咱们跟前两处比一比,这里的树是内核自己的内部结构,叠上去的效果立竿见影:文档的例子里,新节点当场注册成了平台设备。

目标的定位,文档推荐的是标签,理由跟咱们实验里见到的一样直白:只要基础里有这个标签,overlay 就叠得上去了,不用管节点在基础里的具体路径。要是基础编的时候没带 `-@`,标签就查不到了,好在还有按路径的兜底写法 `&{/i2c@800}`,内核文档的原话是此时标签定位不可用,路径定位倒是出路。文档另有一条善后叮嘱:被撤销的节点,内存当场就释放了,别留着指向它们的指针。

配置依赖咱们翻过内核源码 drivers/of/Kconfig(核对的日子是 2026-10-18,主线):`OF_OVERLAY` 是一个 bool 型的开关,提示文本写的是“Device Tree overlays”,选中它的时候会自动带上 OF_DYNAMIC、OF_FLATTREE,OF_RESOLVE 也一并选上了。条目说明里写的定位是“用动态加载的数据,动态修改内核设备树的一部分”。至于从用户态怎么把 overlay 递给内核,overlay-notes 通篇只讲内核的 API,没把它绑在任何用户态的接口上,加载的路径咱们不铺开。运行时叠的典型场景:FPGA 的比特流下载完,对应外设的 overlay 跟着叠进去,硬件是运行中才出现的,所以描述也就在运行中给。

三个位置都走到了,各自的环境、吃的东西与典型场景,咱们摆到一张表里对齐了看。

## 三处的环境与适用范围,对齐了看

| 叠的位置 | 谁来叠 | 吃什么 | 环境与实测状态 | 典型场景 |
| --- | --- | --- | --- | --- |
| 咱们的电脑 | fdtoverlay | 基础 DTB 加若干份 overlay 产物 | 本机 dtc v1.8.1,实测 | 发布前拼产物,产线按订单预拼,叠完反编译核对 |
| 板子的引导阶段 | U-Boot 的 `fdt apply` | 两份产物都带 `-@` 编译 | 未实测,口径出自 U-Boot 官方文档 | 一份镜像伺候一个家族的板子,启动脚本按配件叠 |
| 内核运行之后 | `of_overlay_fdt_apply()` 等 API | 内核活树加 overlay 产物 | 未实测,口径出自内核 overlay-notes | FPGA 比特流配的外设,运行中出现的硬件 |

挑选的依据说到底是一句话:改动定型的时刻越早就越往前叠。出厂就定死的配置,咱们在电脑上叠进产物最省心,核对手艺全在咱们的手里。板子到手才能定的配置,咱们放到引导阶段去叠,镜像还能省下分版的麻烦。硬件要跑起来之后才露面的,内核里的 API 就是唯一的选择了。倒过来的方向走不通,内核里的活树没法退回引导阶段的产物,这也是三处各有各的活的原因。

## 符号表补完,下一章开始排错

“构建系统实际上做了什么”那章咱们初见 `__symbols__`,当时只认了脸。今天全链走通了:基础带 `-@` 编出对照表,overlay 把引用欠成了 fixup,应用器在应用的现场查表回填,fragment 的增量挂到了目标节点上。符号表不是产物里的装饰品,它是三处应用器共同依赖的索引,缺了它,缝合就得退回硬编码路径的老路。

overlay 叠上去了,设备就一定工作吗?未必。描述写得对、叠的时机也对,不过驱动不一定认它、传递链也不一定通,这一层出的问题树自己不会报。所以咱们按层来排查:描述的层、产物的层、传递的层、驱动的层,咱们一层一层地收窄范围。排错的活儿交给下一章,它的名字是“设备没工作,问题在哪一层?”,咱们下一章见。

4. 挑选位置的依据,一句话怎么说?内核里叠好的活树能退回引导阶段的产物吗?
