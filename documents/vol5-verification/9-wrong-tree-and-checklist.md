# 交出去的为什么是另一棵树,带走的清单长什么样?

验到这一层的时候,树本身咱们已经信得过了,咱们要验的是它一路的来历:交到内核手里的,确实是描述这块板的那棵树吗?

## 传递层:树没毛病,交出去的却是另一棵

前四层的毛病都出在树本身,传递层的毛病更冤:树好好的,交到内核手里的却不是这棵。烧错了文件、启动参数指向了别的产物、两块板的 DTB 拿混了,都是这一层的现场。无板的环境里,QEMU 能给咱们一个现成的参照,咱们把 virt 机器自己生成的那棵树导出来:

```shell
qemu-system-aarch64 -M virt -machine dumpdtb=virt.dtb -display none -serial none -nic none
wc -c virt.dtb good.dtb
```

```output
1048576 virt.dtb
    293 good.dtb
1048869 total
```

1048576 字节的 virt.dtb,就是 QEMU 替它的虚拟板准备的基座树,个头接近 mini 产物的三千六百倍。咱们看一眼它的头部:

```shell
xxd -l 40 virt.dtb
```

```output
00000000: d00d feed 0010 0000 0000 0040 0000 1bf4  ...........@....
00000010: 0000 0030 0000 0011 0000 0010 0000 0000  ...0............
00000020: 0000 0239 0000 1bb4                      ...9....
```

头部咱们读三个数:魔数还是熟悉的 d00d feed,totalsize 的值写着 0x100000,大小跟文件本身的长度对上了。结构块的起点是 0x40、长度是 7092 字节,字符串块的起点是 0x1bf4、长度是 569 字节。字符串块的起点加上长度,内容到第 7725 个字节就结束了,咱们用 python 数过,文件其余的部分全是零,QEMU 把它按 1MiB 的整块导了出来。

树里装了什么,咱们把串口与 chosen 摘出来看:

```shell
dtc -I dtb -O dts virt.dtb > virt.dts
sed -n '/pl011@9000000/,/};/p' virt.dts
sed -n '/chosen {/,/};/p' virt.dts
```

```output
	pl011@9000000 {
		clock-names = "uartclk", "apb_pclk";
		clocks = <0x8000 0x8000>;
		interrupts = <0x00 0x01 0x04>;
		reg = <0x00 0x9000000 0x00 0x1000>;
		compatible = "arm,pl011", "arm,primecell";
	};
	chosen {
		stdout-path = "/pl011@9000000";
		rng-seed = <...>;
		kaslr-seed = <...>;
	};
```

rng-seed 与 kaslr-seed 的值每回导出都不一样,咱们用省略号替了,其余的部分咱们原样保留。现在咱们把 mini 产物跟参照树对个位:

- mini 产物里的串口住在 0x1000,virt 的真串口住在 0x9000000,两个地址对不上。
- mini 串口的 compatible 是 `acme,uart`,virt 树里声明的是 `arm,pl011` 与 `arm,primecell`。
- 参照树里有 memory@40000000,chosen 也替内核备好了 stdout-path,mini 产物里两样都没有。

传错树的量级咱们把推演标清楚:把 mini 的 293 字节交给 virt 的内核,等于递给它一张别处板子的地图,串口的地址是错的,compatible 的声明没有任何驱动认,内存的大小没写,启动参数的位子也没留,所以内核大概率连一行日志都发不出来。实测咱们做到了 dumpdtb 导出与反编译对照这一步,内核侧的后果按上面的机制推得。QEMU 的 `-dtb` 选项可以把自备的产物递给内核,它的用法在官方的文档里,启动实验咱们本机没做。

真实板子上咱们验这一层的路子一样:把内核实际收到的 DTB 弄出来,跟板子的现役产物比对字节,两边一致才说明传的树没错。

这一层的验法一句话:咱们交出去的每棵树都核对来历,拿 dumpdtb 导出的参照树跟它对位,树跟板对不上的话,后面的功夫就全白搭了。

五层的现场到这里就走完了,咱们把每层的验法收成一张清单,全课程的收卷也放在这里。

## 五层验法,收成一张排查清单

五层咱们走完了,每层的验法收成一张排查清单,设备失灵的时候你从上往下走:

- 改完源码,你拿反编译核对产物里的值,值没换就重编,时间戳能帮你认产物的新旧。
- 产物每换一次手,你都拿 `dtc -I dtb -O dts` 验读一遍,读得动才算完整。
- compatible 你要跟 binding 逐字符对照,编译器放行了不算数,校验器放行了也不算数。
- 节点在树里却在设备里缺席,你去查 status 的值与驱动的匹配表,再对照 dmesg 的 probe 记录。
- 传递链上每换一次手,你都核对文件与板子的对应,交给内核的产物得描述的确实是这块板。

清单里前两条的取证一条命令就出结果,你把它们走完了,再去动内核侧的验证。每个案例咱们都给过修复前后对照,你自己排错时也照这个标准留证据,修好了拿得出对照,才算真的修好了。

## 收卷:十八个问题走完,下一站是你的板子

咱们走到了这里,第五卷的三个问题走完,全课程的十八个核心问题也走完了。导读开篇的“为什么需要设备树”那篇问过驱动为什么需要外部的描述,“谁会使用设备树”那篇里咱们认过四站,如今产物的字节、binding 的约定、内核的匹配,每一层你都有自己的命令可以作证。课程给你的答案有一条共同的底色:每个判断的背后,都站着你亲手跑过的一条命令。

下一站轮到你的板子了。咱们给你留三件具体的事:

- 把你板子现役的 DTB 拷出来,反编译读一遍,认出串口、内存与 chosen 的位置。
- 把你维护的 DTS 跟它的 binding 对照一遍,compatible 逐字符核过去。
- 下次设备失灵,你按前面的排查清单从产物端走到匹配层,把每一步的证据链记下来。

十八个问题问完了,考卷换成了你自己的板子。排查的章法不变:每一步都拿真实的输入输出来作证,复现不了的层,咱们照样老实写成指引。
